# Case Study Report

## Title

**SKYLINE – Geo-Distributed Weather Monitoring System**

## Topic

Geo-distributed database sharding concepts for high-throughput remote weather
stations.

## Objective

Demonstrate how geographically distributed stations can send readings to an
application that organizes data into region-based logical partitions and
retrieves data using the matching region.

## Problem and proposed approach

Many remote stations produce continuous time-series readings over a wide area.
The case study proposes routing each reading to a controlled regional
collection, so regional queries can focus on the relevant partition. The
approach is intended to make data organization and routing concrete for a
student project.

## Technical scope

The application uses React and Vite in the browser, an Express/Node.js API, and
MongoDB through Mongoose. Region-based collection routing is the selected
logical partitioning approach.

The current implementation includes the dashboard, station management,
simulated monitoring, four logical regional reading collections, Mongoose
schemas, REST APIs, aggregation queries, and an idempotent demo seed script.
Station observations can be sent to the API or generated by the explicitly
simulated monitoring endpoint.

## Geographical query routing and benchmark

The `Geographical Analytics` page demonstrates four API query strategies:

1. **Routed**: resolve a station's assigned region when necessary and read only
   that regional collection.
2. **Scatter-gather**: apply the same query filters to all four collections,
   merge the returned data, and record all four collection accesses.
3. **Multi-region**: query only the selected region collections.
4. **Global**: query all four collections without a regional filter.

For the South case study, the benchmark compares the same South-region
predicate, station/time filters, sort order, and result cap. The routed
operation targets `south_weather_readings`; scatter-gather checks the same
predicate in all four collections. A separate global scenario returns
observations across all regions. Collection access counts make the routing
difference explicit; they do not prove a guaranteed latency improvement.

The API times actual result retrieval and separately requests MongoDB
`explain("executionStats")` for documents examined/returned, keys examined, and
winning-plan index names. Missing explain metrics appear as `N/A`; the
implementation does not inject artificial delays or manufacture measurements.
The benchmark uses a small academic sample and runs on the configured MongoDB
environment, so measurements are specific to data size, warm/cold cache,
indexes, hardware, and current load. No fixed latency claim is made. Recent
query history is process-local and resets when the API restarts.

## Indexing rationale

Regional collections use `{ stationId: 1, recordedAt: -1 }` for station
history, `{ region: 1, recordedAt: -1 }` for region/time analysis, and
`{ recordedAt: -1 }` for time-only queries. The compound indexes replace
separate stationId/region indexes through their prefixes. Seed idempotency uses
a unique sparse `seedKey`. Stations use unique `stationId`, region/status
filtering, standalone status filtering, and a `2dsphere` GeoJSON index.

## Demonstration results and interpretation

The validation report documents three South-region runs against the same
filter and 50-record result cap. Routed and scatter-gather strategies returned
the same 50 records. Routed accessed one regional collection; scatter-gather
accessed all four. Observed API timings were 15.768/49.702 ms, 6.549/147.760
ms, and 8.627/379.350 ms (routed/scatter-gather). Each observed run examined
50 documents for the returned results and used the `region_1_recordedAt_-1`
index. These are measurements from the tested local deployment only.

A separate 12-sample alternating indexed/forced-collection-scan test returned
10 records for each strategy. Median observed elapsed times were 6.738 ms for
the indexed strategy and 9.331 ms for the forced scan; explain examined 10
versus 50 documents and 10 versus 0 keys. The local sample is small and timing
had outliers. See [TESTING_REPORT.md](TESTING_REPORT.md) for test methodology,
individual observations, and limitations.

The result supports a structural observation—regional routing accessed fewer
collections in these regional comparisons—not a universal claim that routed
queries execute faster. Performance depends on dataset size, indexes, cache,
hardware, database environment, and load.

## Important limitation

The project does not configure or claim to run a production MongoDB sharded
cluster. Regional collections on a single deployment demonstrate logical
application-level partitioning only. Native MongoDB sharding would require
separate cluster configuration, shard keys, and deployment/testing beyond this
academic foundation.
